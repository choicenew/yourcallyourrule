# 用户核心架构要求与重构沉淀规范 (SYNC_ARCHITECTURE_REFACTORING_SPEC.md)

---

## 一、 用户核心架构法则与重构原则

### 1. 中央数据库与 Sync 数据库本质统一（同一个底座，绝不重复造轮子）
* **底座统一**：中央数据库与 `packages/sync/` 下面的数据库，**它们的核心本质就是同一个东西**。架构上绝对不重复造轮子！
* **接口判定与多态角色**：它们俩完全共享同一个基础核心引擎，区别仅仅在于接入了什么接口：
  * **接入中央数据库接口**：它就充当系统中央数据库，提供中央数据服务；
  * **接入用户同步接口**：它就充当用户个人数据的云盘/网盘同步工具。

---

### 2. 众包数据库的标准化分支与按需独立接入
* **标准协议实现**：众包数据库和中央数据库一样，同样是基于标准协议（Protocol）与 Hub / Adapter 体系来实现的。
* **不绑死底层存储**：众包数据库是标准协议派生出来的独立分支，支持自由更换底层存储（绝对不假设只用 Cloudflare，以后也可以用 Supabase 或自建服务器）。
* **独立按需接入**：众包做成独立的分支，将来 App 需要什么样的众包（规则众包、书源众包、黑名单众包等），就去独立接入什么样的众包。众包独立存在，不强行绑定在中央数据库或个人同步里。

---

### 3. 云盘同步的纯粹网盘定位与彻底否决主从设备
* **纯粹网盘定位**：留在 `sync` 目录下的同步功能，纯粹是创造用户的个人数据同步功能，类似于一个网盘，只需要实现对应的简单接口就行了（与 Supabase / Cloudflare 原理一致）。
* **彻底否决主从设备**：云盘同步完全不需要主从设备，在云盘同步里引入主从设备是臃肿的错误设计。云盘同步天然是多端平权的，只需要实现对应的简单同步接口即可。
