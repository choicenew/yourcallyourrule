# `pyro_sync_database` 架构与实施规划

## 一、 这个包到底是什么东西？（为什么不用旧的 supabase 包）

在老的架构中，我们有一个 `supabase_sync_package`，它是一个和业务高度耦合的“旧包”。
为了实现 `Protocol & Hub` 的解耦，我们需要一个全新的包：**`pyro_sync_database`**。

它的唯一功能是：**作为增量同步（实时同步）的通用消费者**。它向下从 `pyro_sync_hub` 拿取各业务线的 `SyncDataAdapter`，向上对接云端数据库（如 Supabase）。

## 二、 架构设计的根本冲突与解决方案

### 1. 为什么坚决不能在 `pyro_sync_protocol` 里面捏造 SQL 查询接口？
之前我们陷入了一个严重误区：想要把 `syncitron`（一个基于轮询、需要追踪本地数据库 `is_synced` 脏标记、需要执行 SQL 查询的重型引擎）直接套用在业务的 `SyncDataAdapter` 上。
# Pyro Sync Database 架构与执行计划

## 一、 包的定位与核心目标

`pyro_sync_database` 是整个 `pyro_reader` 同步架构中**最高层的整合包（Consumer 层）**。
它的根本任务是提供**开箱即用**的同步能力和 UI，而**绝不包含任何复杂的底层数据转换与脏数据管理逻辑**。

## 二、 核心架构设计：彻底的“拿来主义”与组件拼装

之前的误区在于试图在这个包里大包大揽地写一个带垃圾回收的 Isar 数据库，这导致了包的逻辑极度臃肿。
现在的架构逻辑完全回归“拼装与整合”：

### 1. 脏活外包：依赖独立的适配器包
所有的架构阻抗（比如怎么把 0 感知的业务流转换成带元数据的同步底层数据），全部扔进专门新建的 `sync_adapter_syncitron` 包里去处理。
本包只需在 `pubspec.yaml` 中引入该包，无需关心其内部复杂的过渡区和 GC 实现。

### 2. 纯粹的路由分配与初始化胶水
`DatabaseSyncManager` 仅仅作为一个薄薄的代理配置中心：
- 读取 `SyncHub` 中的业务适配器。
- 将这些业务适配器传递给 `sync_adapter_syncitron` 暴露的极其简化的工厂方法。
- 一键启动配置好的同步引擎。

### 3. UI 外壳统筹
将底层的 UI 组件（如 `SyncStatusWidget`、`SyncButton` 等）在这个包中统一包裹和重导出（export），使得业务线可以通过极简的方式直接贴到界面上，而不需要关心背后的引擎是 `syncitron` 还是未来的某个新包。

## 三、 执行步骤 (开发者的实施红线)

1. **绝对轻量化**：本包内**禁止**出现任何对 Isar、SQLite 的直接引用或操作代码。**禁止**编写底层状态转换逻辑。
2. **纯粹的组装厂**：代码必须保持克制，只做类实例的装配、配置注入和顶层生命周期的控制。
3. **暴露 UI**：确保外部应用只需依赖此包，就能拿到完整的离线/同步 UI 组件库。
